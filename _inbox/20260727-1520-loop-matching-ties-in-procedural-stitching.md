# Least-squares loop matching is ill-conditioned when the bridge is long

## Problem
A parametric character generator stitched limbs into a torso by cutting a hole
and bridging the hole loop to the limb's first ring. The matcher picked the
rotation minimising the sum of squared distances between corresponding points.

Two independent symptoms, both invisible to every existing gate:

1. Four of eight seams (the fingers) had **two rotations whose sums were equal
   to within 2e-16 relative** - an exact tie. Which one won depended purely on
   floating-point rounding order.
2. The shoulder seam had best and second-best differing by **2%**. Moving one
   unrelated slider ("posture", which shears the torso slightly) flipped the
   choice, changing 24 faces.

The generator's core promise was "topology is identical at every slider setting,
so bone weights and clothing transfer between body shapes". That promise was
silently false.

## Root cause
The bridge between the hole and the limb ring has a **length along the limb
axis**. That axial offset enters the distance sum identically for *every*
candidate rotation, so it dominates the total and swamps the shape difference
the matcher is actually trying to resolve. The longer the bridge relative to
the ring radius, the flatter the objective function.

The finger ties came from a second cause stacked on the first: a rectangular
hole patch (3x1 faces) has near-fourfold symmetry, so several rotations are
genuinely equivalent.

## Solution
Two changes, both cheap:

1. **Stop using distance for the correspondence. Pin it by angle.** Both loops
   are generated by code, so both have a known parameterisation. Assign each
   hole-boundary vertex an angle (spread evenly around the loop, anchored on a
   reference direction) and pair it with the ring point at the same angle. No
   search, no tie, no dependence on rounding.
2. **Add a relative tie-break epsilon** to any remaining least-squares matcher:
   a candidate wins only if it is better by more than ~1e-9 relative, so ties
   resolve to a deterministic first-found instead of to numerical noise.

Also worth doing: reshaping the rectangular hole into an ellipse removes the
symmetry that caused the exact ties in the first place.

## The gate that should have existed
Build the mesh at every slider extreme, at the midpoint, and at
default + 1e-6 * range, then compare the **face list** byte for byte. This
found both bugs immediately and is cheap (320 builds ran in seconds). Any
generator that promises stable topology needs this gate from day one.

## What didn't work
- Tightening the epsilon in the matcher. The shoulder case is not a tie, it is
  a genuine 2% difference that legitimately flips - no threshold fixes it.
- Assuming the vertex count staying constant meant the topology was constant.
  Vertex count, island count, watertightness and volume were all unchanged and
  green while the face list differed.

## Transferability
Applies to any procedural mesh system that bridges two generated loops:
character generators, modular building kits, pipe/cable systems, procedural
foliage, terrain stitching. Anywhere "find the best rotation between two rings"
appears, check whether the objective is dominated by a constant offset.

The failure mode is especially nasty because it is *invisible* to the usual
mesh-integrity checks and only surfaces much later, when skinning or UVs stop
transferring between variants.
